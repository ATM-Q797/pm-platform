## 二、8-2 项目健康度评级（规则灯）

### 2.1 目标
给决策者一个**一目了然的风险信号**，用于排优先级；**不是考核工具**（见 §2.5）。
评级形态 = **规则灯**（用户 2026-11-06 裁定）：只认事实，事实直接触发档位，一行短语即懂、当场可对照项目数据核验——无分数、无小数、无分母、无公式。

### 2.2 事实规则（规则灯：事实触发档位，无分数）

| 事实 | 触发 | 档位 | 短语 |
|---|---|---|---|
| 阶段逾期 ≥7 天未完成 | 有 1 个即触发 | 🔴 红（风险） | 1个阶段逾期X天 / N个阶段逾期最长X天 |
| 阶段逾期 1–6 天 | 有 1 个即触发 | 🟡 黄（关注） | 同上 |
| 资源冲突 ≥3 对（阶段对去重） | 达 3 对触发 | 🟡 黄（关注） | 资源冲突N对 |
| 无阶段 / 活跃阶段均无计划日期 | 无法判定 | ⚪ 灰（未评估） | 未评估（detail 按成因分句） |
| 有事实 + 部分活跃阶段无计划日期 | 事实定档 | 按事实 | 主因短语 + 附注「N 个活跃阶段无计划日期，未纳入判定」 |
| 无事实 + 存在无计划日期的活跃阶段 | 无法判定全貌 | ⚪ 灰（未评估） | 未评估（不冒充正常） |
| 以上均无（含全部阶段已完成的项目） | — | 🟢 绿（正常） | 正常 |

**档位规则**：有红事实 → 红；否则有黄事实 → 黄；无法判定 → 灰；否则绿。多事实同现只显示最严重一条短语（红 > 黄，同档逾期 > 冲突）。

**短语口径**：N = 全部逾期阶段数（含 1–6 天档），X = 最长逾期天数（渲染串：单逾期「1个阶段逾期X天」，多逾期「N个阶段逾期最长X天」）；事实只来自有日期的活跃阶段（状态 ∉ {已完成, 搁置}），完成阶段不产生逾期，冲突对按 detect_conflicts 口径（完成/搁置阶段不参与，本层再按活跃阶段 id 过滤）。

**阈值出处**（评审 #2 #2 补）：≥7 天红 / 1–6 天黄与「N个阶段逾期X天（取最长）」出自 2026-11-06 呈报并经用户同日批复「好，按照现在的方案开始执行。」的方案 B 事实清单原文；7 天界与「即将到期 7 天」窗口对称（内部一致性）；冲突 ≥3 对出自用户同日指令「资源冲突阈值改 ≥3 对才预警」。

**口径复用**：逾期 = 阶段 `plan_end` < 今天且状态 ∉ {已完成, 搁置}（与看板「延期项目」同源）；冲突 = `resource_conflicts.detect_conflicts` 按 (phase_a_id, phase_b_id) 对去重（与 8-1 风险队列同源）；1–2 对冲突属资源常态占用，不预警。

**搁置项目不评**（列表显「—」，详情不展示，不上风险清单）；专项在查询层排除（与看板/快照同口径）。

### 2.3 界面
- 项目列表「健康度」列：色点 + 主因短语（如 `● 1个阶段逾期16天`），无分数无 hover 依赖；
- 项目详情健康度区：档位徽章 + 事实清单（带对象名，如「阶段「配置评估」逾期 16 天（plan_end …）」）+ 固定文案；
- 看板「风险分析」弹窗（2 分板块）：🔴 红档·立即处理 / 🟡 黄档·需要关注，行 = `● 项目名（负责人）主因短语`（负责人 = 项目 `Project.owner`），点行跳项目详情；今日风险内容不入此弹窗——延期行由看板「今日聚焦」卡（= §一 功能 2「今日风险队列」的现行卡名，DashboardPage 实现名）的延期项目区承接、到期行由「即将到期」卡承接、冲突行由「资源冲突」卡与冲突明细抽屉承接；绿/灰不入弹窗、不上风险清单。

### 2.4 关键设计约束
1. **一目了然**：任何一行短语即懂、当场可对照项目数据核验——无分数、无小数、无分母、无公式；
2. **缺数据不猜**：无法判定 → 灰档「未评估」，不冒充绿；
3. **口径单一来源**：评级逻辑放 `services/health_score.py`，看板/列表/详情三处调用同一函数。

### 2.5 明确不做
合成评分/加权分、机器学习打分、跨项目排名榜单（易被误用为绩效考核）、按人打分。

### 2.6 验收
- 任一风险项目的一行短语可当场对照项目数据核验（如「1个阶段逾期16天」→ 该阶段 plan_end = 今天−16）；
- 无计划日期的项目显示「未评估」，不冒充正常；
- 同一项目在看板、列表、详情三处档位与短语一致；
- 边界（评审 #2 #4 补）：逾期 6 天黄 / 7 天红（含界）；冲突 2 对不亮 / 3 对亮黄；红黄同现 reason 取红短语、同档取逾期短语；
- 搁置项目列表显「—」、详情区隐藏、不上风险清单；绿/灰不入风险分析弹窗；
- 部分缺计划日期：有事实按事实定档并附注未判定阶段数；无事实显「未评估」（不冒充正常）。

### 2.7 数据契约（v2）
- 服务：`assess_health(project, phases, conflicts, today) -> HealthStatus{band, reason, facts[], disclaimer}`；`assess_projects(projects, conflicts, today) -> {project_id: HealthStatus}`（搁置不入表）；`longest_overdue_days`（风险行排序键）。
- 事实：`HealthFact{kind: delay|conflict|nodata|clear, phrase, detail, severity}`——severity 2 = 红事实，1 = 黄事实，0 = 注记/正常。
- 端点：`GET /api/projects` 随行 `health`（搁置 null → 「—」）；`GET /api/projects/{id}/health`（搁置 409 / 专项 403 / 其余 200）；`GET /api/dashboard/stats` → `risk_projects: ProjectHealthSummary{project_id, project_name, owner, status, band, reason, overdue_days}[]`（只含红/黄，红档在前、逾期久在前；owner = 项目 `Project.owner`，同 §2.3 负责人取数口径）。
- 弹窗宿主与入口：看板头部「风险分析」按钮 → `DashboardPage` 内 Modal（风险卡已撤，入口唯一）。
- 防火墙固定文案（「本评级为项目状态参考，不构成绩效考核」）落点 = 详情健康度区 + 风险分析弹窗底部；列表列不带（避免列宽噪音）。

## 三、8-3 按项目维度的历史趋势

### 3.1 问题
现有趋势是**全局**口径（项目总数、完成数…），看不出「单个项目的进度是怎么走过来的」。项目详情页目前只有当前状态。

### 3.2 现状核查（实证）
`status_snapshots` 表结构：`snapshot_date`（唯一）+ `metrics` JSON + `created_at`（`models/status_snapshot.py:22-24`），metrics 为全局原子计数，**无 project_id 维度**。因此项目级历史**无法从现有快照回溯**。

### 3.3 已选定方案 A（用户 2026-11-04 批复），带存储优化口径③

新表 `project_snapshots(project_id, snapshot_date, metrics JSON, project_code, project_name)`，唯一约束 `(project_id, snapshot_date)`；与全局快照同一 crontab 任务内写入。

**存储口径③（用户认可）**：
- 只拍**在办项目**（未开始/进行中）；已完成/搁置项目**冻结**，不再产生新行
- **分层降采样**：90 天内日粒度 → 2 年内周粒度（周一锚点）→ 2 年以上月粒度（月初）
- 单项目一生约 200 行（对比日粒度永久保留的 3,650 行）
- 10 年累计约 100–150 MB（对比原设计的 1.0 GB）

**追溯设计（用户认可「删项目要能追溯」）**：
- 快照行内冗余 `project_code` + `project_name`（快照时点值，不依赖项目行）
- 外键 `project_id ON DELETE SET NULL`（**不用 CASCADE**）
- admin 端加「历史项目」列表：按 `project_code` 查被删项目的历史曲线
- 追溯三层链：①删除申请/审批记录（`project_delete_request`）→ ②`operation_log`（何时删的）→ ③保留的历史快照（项目当时怎么走的）
- 副作用（已认可）：名字冻结在删除时刻；UI 按编号聚合、显示最后一次名字

### 3.6 存储与追溯评估（2026-11-04 实测基线 + 用户批复）

**实测基线**（生产 `10.53.9.38`，PG 16）：整库 9.8 MB；79 项目 / 420 阶段；`status_snapshots` 4 行、单行 JSON 708 B、含索引 48 kB。

**增长预估**（口径③，年增 100 项目）：

| 年 | 在办项目数 | 年增行数 | 累计行数 | 累计体积 |
|---|---|---|---|---|
| 1 | ~129 | 4.7 万 | 4.7 万 | ≈ 22 MB |
| 3 | ~329 | 12 万 | 25 万 | ≈ 118 MB |
| 5 | ~529 | 19 万 | 60 万 | ≈ 280 MB |
| 10 | ~1,029 | 37.5 万 | 211 万 | ≈ 1.0 GB |

**口径③优化后**：只拍在办项目 + 分层降采样（90 天日 / 2 年周 / 以后月）→ 10 年约 **100–150 MB**，接近线性。

**垃圾/碎片三来源与处置**：

| # | 来源 | 处置 |
|---|---|---|
| 1 | 同日重复写入（手动刷新/任务重跑） | `UNIQUE(project_id, snapshot_date)` + upsert 幂等；PG autovacuum 分钟级回收 |
| 2 | **项目删除后孤儿行** | 外键 `SET NULL` + 快照内冗余编号/名称；admin「历史项目」入口可查 |
| 3 | 日明细无限累积 | 分层降采样（口径③）+ 保留策略：日粒度留 90 天，周粒度留 2 年，月粒度永久 |

**不需要做的事**（避免过度设计）：分区表（要到 1000 万行才值得）；调 autovacuum（79 行/天）；定期 REINDEX；额外监控（日常日志输出表大小即可）。

### 3.4 方案 A 的功能
- 项目详情新增「进度趋势」区：X 轴日期，两条线——**计划累计完成度**（按阶段计划排期算）与**实际累计完成度**（按快照里的阶段进度/完成数算）；缺口即偏差。
- 叠加标记：延期阶段数、冲突数在同一图上以事件点标注。
- 时间窗可选 30 / 90 / 365 天。

### 3.5 验收
- 当日快照写入后，详情页趋势末点与看板当日数字一致；
- 缺失日期（服务停机）在曲线上断开而非补零；
- 单项目单日重复触发不产生两行（唯一约束兜底，与全局快照同款）。

## 四、8-4 团队效率统计

### 4.1 目标
回答「人够不够、谁被压住了、哪些环节老返工」——**工作负荷参考，不做绩效排名**。

### 4.2 指标

| # | 指标 | 计算 | 数据来源 | 备注 |
|---|---|---|---|---|
| 1 | 在办项目数 | 每人当前承担（阶段负责人）的未完成阶段所属项目去重计数 | `PhaseAssignee` → `Phase` → `Project` | 排除专项/搁置 |
| 2 | 峰值并行 | 复用热力图 `peak_parallel`（12 周窗） | `resource_heatmap` | 已有实现 |
| 3 | 按期完成率 | 已完成阶段中 `actual_end ≤ plan_end` 的占比 | `Phase.actual_end/plan_end` | 需 actual_end 真实填写；缺失时单独列为「未记录完成日」不计入分母 |
| 4 | 返工率 | 返工次数 > 0 的阶段 ÷ 该人负责的已完成阶段 | `Phase.rework_count` | 口径自足（`rework_count > 0` 计数与看板「返工次数」卡同源；8-2 规则灯无返工维） |
| 5 | 平均阶段周期 | `avg(actual_end − actual_start)`，按人聚合 | `Phase.actual_start/actual_end` | 缺一头不计入 |
| 6 | 负荷分布 | 按岗位（`Resource.role`）聚合在办项目数，看瓶颈岗 | `Resource.role` | — |

### 4.3 界面
独立页「团队效率」（admin / manager 可见，与用户管理同级），表格 + 两张图（负荷分布、返工率 Top）。**不做**个人排名榜，默认顺序按姓名，用户可自行排序。

### 4.4 关键约束
1. **数据质量先声明**：`actual_start / actual_end` 为手工填写，未填比例在页面顶部显示「完成日记录率 X%」——指标可信度先让使用者知道。
2. **不生成考核结论**：页面固定文案说明「本页为负荷与流程分析，不构成绩效评价」。
3. 冲突口径与 8-2/8-1 同源（`resource_conflicts.detect_conflicts`）；返工口径按 `Phase.rework_count` 自有定义（与看板「返工次数」卡同源），不依赖 8-2。

### 4.5 验收
- 每人各项指标可从阶段明细复算；
- 完成日记录率与库中实际空值比例一致；
- 排除专项后与看板人员数一致（活跃人员口径对齐热力图）。
