### 1.1 目标

### 1.2 功能点

| # | 功能 | 说明 | 数据来源 | 优先级 |
|---|---|---|---|---|
| 1 | **环比标记** | 看板每张卡显示「较上周 +N / −N」小字（绿降红升，延期类上升为红） | `build_trend` 的周差分（已有 `completed_projects_total` / `shelved_total` / `started_projects_total`）+ 新增延期/冲突周差分 | P0 |

| 3 | **口径内嵌说明** | 每个指标旁「?」气泡，写明计算口径（例：「延期 = 阶段 plan_end < 今天 且状态 ∉ {已完成, 搁置}，排除专项」） | 静态文案 | P1 |

## 二、8-2 项目健康度评分

### 2.1 目标
给项目负责人一个**可解释的红黄绿信号**，用于排优先级；**不是考核工具**（见 §2.5）。

### 2.2 评分模型（100 分制，逐项可追溯）

| 维度 | 权重 | 计算 | 数据来源 |
|---|---|---|---|
| 进度达成 | 35 | 机会分 = 35 × (实际进度% ÷ 应达进度%)，封顶 35；应达进度按 `(今天 − plan_start) ÷ (plan_end − plan_start)`，未开始或日期缺失按 0 分并标注「无计划基线」 | `Project.plan_start/plan_end`、阶段 `progress` 加权均值 |
| 延期暴露 | 25 | 无延期阶段 25 分；有延期按 `max(0, 25 − 延期阶段数×5 − 最长延期天数÷2)` 扣减 | 阶段 `plan_end` vs 今天、`status` |
| 返工频次 | 15 | 15 − 返工次数×5（下限 0）；返工指 `Phase.rework_count > 0` 累计 | `Phase.rework_count` |
| 资源冲突 | 15 | 15 − 该人/该项目参与冲突对数×5（下限 0） | `resource_conflicts.detect_conflicts` |
| 计划合理性 | 10 | 计划工期 ∈ [7, 120] 天得 10；<7 或 >120 得 0 并在明细标注「工期异常」 | 项目 `plan_start/plan_end` |

**分档**：≥80 健康（绿）/ 60–79 关注（黄）/ <60 风险（红）。

### 2.3 界面
- 项目列表新增「健康度」列（色块 + 分数，hover 显示五项明细）；
- 项目详情顶部一行总分 + 五维雷达/条形；
- 看板新增「风险项目 N 个」卡，点开为分数升序列表。

### 2.4 关键设计约束
1. **必须可解释**：任何分数都要能展开看到「哪一项扣了多少、为什么」；不解释的分数没人会信。
2. **缺数据不猜**：计划日期缺失 → 该项不计分并显式标注（分母相应缩减），不用 0 分冒充「做得差」。
3. **口径单一来源**：评分逻辑放 `services/health_score.py`，看板/列表/详情三处调用同一函数。

### 2.5 明确不做
机器学习打分、跨项目排名榜单（易被误用为绩效考核）、按人打分。

### 2.6 验收
- 任一项目分数可逐项复算，五项之和 = 总分；
- 缺计划日期的项目不出现「无理由 0 分」，明细写明「无计划基线，仅按可算维度计分」；
- 同一项目在看板、列表、详情三处分数一致。

## 三、8-3 按项目维度的历史趋势

### 3.1 问题
现有趋势是**全局**口径（项目总数、完成数…），看不出「单个项目的进度是怎么走过来的」。项目详情页目前只有当前状态。

### 3.2 现状核查（实证）
`status_snapshots` 表结构：`snapshot_date`（唯一）+ `metrics` JSON + `created_at`（`models/status_snapshot.py:22-24`），metrics 为全局原子计数，**无 project_id 维度**。因此项目级历史**无法从现有快照回溯**。

### 3.3 两个方案（需你选）

| 方案 | 做法 | 成本 | 代价 |
|---|---|---|---|
| **A. 新增项目级快照表（推荐）** | 新表 `project_snapshots(project_id, snapshot_date, metrics JSON)`，唯一约束 `(project_id, snapshot_date)`；与全局快照同一 crontab 任务内写入 | 1 张表 + 1 次迁移 + 采集函数 | **历史从上线日开始积累**，上线前的曲线没有 |
| B. 不存历史，只做当前偏差 | 项目详情显示「计划 vs 实际」当前对比（进度条、偏差天数），不做时间轴 | 极小，零迁移 | 没有趋势曲线，只有此刻快照 |

**建议 A**：数据量可控（75 项目 × 365 天 ≈ 2.7 万行/年），且它是 8-4 的一部分基础。若你希望「先看到东西再说」，也可先做 B 再升级到 A（B 的界面在 A 落地后继续复用，不浪费）。

### 3.4 方案 A 的功能
- 项目详情新增「进度趋势」区：X 轴日期，两条线——**计划累计完成度**（按阶段计划排期算）与**实际累计完成度**（按快照里的阶段进度/完成数算）；缺口即偏差。
- 叠加标记：延期阶段数、冲突数在同一图上以事件点标注。
- 时间窗可选 30 / 90 / 365 天。

### 3.5 验收
- 当日快照写入后，详情页趋势末点与看板当日数字一致；
- 缺失日期（服务停机）在曲线上断开而非补零；
- 单项目单日重复触发不产生两行（唯一约束兜底，与全局快照同款）。

## 四、8-4 团队效率统计

### 4.1 目标
回答「人够不够、谁被压住了、哪些环节老返工」——**工作负荷参考，不做绩效排名**。

### 4.2 指标

| # | 指标 | 计算 | 数据来源 | 备注 |
|---|---|---|---|---|
| 1 | 在办项目数 | 每人当前承担（阶段负责人）的未完成阶段所属项目去重计数 | `PhaseAssignee` → `Phase` → `Project` | 排除专项/搁置 |
| 2 | 峰值并行 | 复用热力图 `peak_parallel`（12 周窗） | `resource_heatmap` | 已有实现 |
| 3 | 按期完成率 | 已完成阶段中 `actual_end ≤ plan_end` 的占比 | `Phase.actual_end/plan_end` | 需 actual_end 真实填写；缺失时单独列为「未记录完成日」不计入分母 |
| 4 | 返工率 | 返工次数 > 0 的阶段 ÷ 该人负责的已完成阶段 | `Phase.rework_count` | 与 8-2 同一口径 |
| 5 | 平均阶段周期 | `avg(actual_end − actual_start)`，按人聚合 | `Phase.actual_start/actual_end` | 缺一头不计入 |
| 6 | 负荷分布 | 按岗位（`Resource.role`）聚合在办项目数，看瓶颈岗 | `Resource.role` | — |

### 4.3 界面
独立页「团队效率」（admin / manager 可见，与用户管理同级），表格 + 两张图（负荷分布、返工率 Top）。**不做**个人排名榜，默认顺序按姓名，用户可自行排序。

### 4.4 关键约束
1. **数据质量先声明**：`actual_start / actual_end` 为手工填写，未填比例在页面顶部显示「完成日记录率 X%」——指标可信度先让使用者知道。
2. **不生成考核结论**：页面固定文案说明「本页为负荷与流程分析，不构成绩效评价」。
3. 与 8-2 共用返工/冲突口径函数，避免两处算法漂移。

### 4.5 验收
- 每人各项指标可从阶段明细复算；
- 完成日记录率与库中实际空值比例一致；
- 排除专项后与看板人员数一致（活跃人员口径对齐热力图）。

1. 每项指标**可复算**（页面数字与库查询一致，抽样核对）；

3. 缺数据显式标注，不用 0 冒充；
4. `pytest` 全绿 + `tsc` 零错 + `npm run build` 通过；
5. 内网无外网依赖，全部功能在 `10.53.9.38` 可运行。

## 七、风险与对策

| 风险 | 对策 |
|---|---|
| 8-3/8-4 历史数据只有上线后才有 | 方案 A 明确「历史从上线日积累」；页面在数据不足 7 天时显示「数据积累中（尚需 N 天）」 |
| `actual_start/actual_end` 大量未填 | 8-4 顶部显示「完成日记录率」；未记录阶段不计入分母并在明细可查 |
| 健康度被当成绩效考核 | 页面与文档双处声明「不构成绩效评价」；不生成排名榜 |
| 口径争议（延期/搁置/专项） | 全部沿用 2026-10-26 既定裁定；新增指标逐条在本文件写明口径，评审时核对 |

## 八、建议实施顺序
**8-1（环比 + 风险队列）→ 8-2（健康度）→ 8-4（团队效率）→ 8-3（项目趋势，需迁移）**

理由：8-1 零迁移、当天可见；8-2 纯计算、无历史依赖；8-4 依赖 8-2 的返工/冲突口径函数；8-3 需建表与数据积累，放最后。
