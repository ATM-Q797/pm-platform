# 信息填报模块设计方案（替代腾讯共享文档）

> **版本**: v1.2 | **日期**: 2026-10-28 | **状态**: 已批准（round-2 评审 pass，5 口径点已裁定）
> **来源**: 用户 2026-10-28 需求描述 + 《样例/项目填报模板表.xlsx》字段模板与 11 条说明（全文见 §十三）
> **定位**: 新增独立填报页面，供项目组同事在浏览器中完成原本在腾讯共享文档里做的项目/阶段信息填报；上线过渡期通过「填报人」角色收敛可见页面。

---

## 一、目标与边界

**目标**：把"腾讯共享文档多人填一张表"搬到平台里，用表单+权限替代人工维护。字段口径与现有平台完全一致，本质是给现有 Project / Phase 数据一个"按填报人视角组织"的入口。

**不做**（本期边界）：
- 不改现有页面（项目列表/看板/资源/甘特保持原样，仅对「填报人」隐藏导航）；
- 不做填报页 Excel 导入（既有导入功能不变）；
- 不做站内消息通知（审批结果页面刷新可见，通知留二期）。

## 二、模板表字段 → 平台字段映射（14 列，已对照模型核实）

不新建业务表，全部落现有 Project / Phase：

| 模板列 | 平台落点 | 说明 |
|---|---|---|
| 项目编号 | Project.code | 自动生成、只读。**普通项目**取非专项项目的纯数字编号最大值 + 1（跳过已被占用的编号值）；**专项项目单独核算、不占用项目编号**——专项走独立 ZX 系列（ZX001 起，`_next_special_code`），不进入普通数字序列 |
| 项目类目 | Project.category | 新建三选一：新需求/改造/量产（定制归一为新需求）；存量"定制"值兼容显示 |
| 项目名称 | Project.name | 文本 |
| 项目负责人 | **Project.managed_by**（user_account 外键）+ owner 文本存显示名 | =整机设计师。判定口径：managed_by 命中账号即负责人；**未关联账号（Excel 导入项目）按 owner 文本 = 账号名回退**（`is_project_manager` / `is_project_owner`，用户 2026-10-30 裁定）——负责人判定与权限判定同源，不脱节 |
| 市场 | Project.market | 10 项枚举，与现有下拉一致 |
| 项目状态 | Project.status | 未开始/进行中/已完成/搁置（取消=搁置） |

| 阶段类型 | Phase.phase_type | 平台 10 类；阶段名 name 自动取类型显示名（PhaseEditor 已去名称输入的先例） |
| 计划开始/结束 | Phase.plan_start / plan_end | **仅项目负责人可改**；阶段负责人改→走审批（§四） |
| 实际开始/结束 | Phase.actual_start / actual_end | 阶段负责人填 |
| 阶段负责人 | **Phase.assignees**（Resource 多对多，phase_assignee 表） | 项目负责人指派；多人兼容（导入侧已有顿号拆分先例） |
| 阶段状态 | Phase.status | 平台枚举全量开放：未开始/进行中/已完成/延期/搁置（平台为模板的超集） |

## 三、角色设计

### 3.1 新增「填报人」角色（reporter）

- `user_account.role` 为应用层字符串（`user.py:29`），增加 `reporter` 值，**零 DDL**；
- **可见范围**：登录后导航与路由只有「信息填报」一个页面；默认落地页跳 `/report`（`App.tsx:109` defaultPath 增分支）；其余页面菜单不显示、直敲 URL 一律重定向回 `/report`（沿用现有 Route 角色守卫模式，`App.tsx:262-292`）。**admin 导航亦含「信息填报」入口**（用户 2026-10-29 追加指令：管理员需可见可操作；admin 页面导航不隐藏其余页面，数据权限仍按 §3.2 人×项目关系判定）；
- **权限范围**：reporter 对既有 `/api/*` 的封锁由**应用层统一封锁门**实现（`main.py` 全局中间件：reporter 访问 `/api/report/*`、`/api/auth/*` 以外的一切 `/api/*` 一律 403）。原设计假设既有接口全部经 `require_role` 白名单默认拒绝，实测不成立（多数旧接口仅要求登录），故不改任何旧路由，在应用层统一设门；封锁面以 §八 测试矩阵核验；
- **过渡定位**：后期项目组人员转正式角色后不再新增 reporter 用户，角色本身保留。

### 3.2 填报页内三种数据级身份（按"人 × 项目/阶段"关系判定，服务端强校验）

| 身份 | 判定依据 | 能做什么 |
|---|---|---|
| 项目负责人（整机设计师） | `project.managed_by == user.id`；未关联账号时按 owner 文本 = 账号名回退（用户 2026-10-30 裁定） | 新建项目；改项目级字段；改任意阶段计划时间（直接生效）；指派阶段负责人；审批改期申请 |
| 阶段负责人 | user.resource_id → 该阶段 assignees 包含此 Resource | 填该阶段实际开始/结束；改该阶段状态/进度/备注；对计划时间发起改期申请 |
| 其他填报人 | 以上皆非 | 只读其可见项目；不可编辑任何字段 |

## 四、改期审批流（模板说明第 6 条）

**复用既有 `phase_change_request` 表与模型（`audit.py:63-85`），零 DDL**——不建新表。该表即 Phase 5.3 工程师阶段审批所用（engineer 提交 → manager 复核），字段完全够用：

- `proposed_changes`（JSON Text）承载变更提案，填报流格式：`{"plan_start": {"old": "...", "new": "..."}, "plan_end": {"old": "...", "new": "..."}}`；
- `status`（pending/approved/rejected）、`reviewed_by`、`review_comment`（驳回原因）、`created_at`、`reviewed_at` 均现成；
- **审批人不同**：现有流程复核人是 admin/manager（既有 `/api/phase-change-requests` 接口保持不动）；填报流由**项目负责人（managed_by）**审批——新增 `/api/report/*` 三个接口操作同一张表，权限按填报流判定。入口独立（§九-4 已裁定），不进现有审核中心页面。

**流程**：
1. 阶段负责人在填报页修改某阶段计划时间 → 弹确认"将提交改期申请给项目负责人" → 写入 pending 申请（不落 Phase）；
2. 项目负责人在填报页「待我审批」批准 → 应用新计划时间到 Phase + 写 `operation_log`（复用 `audit.py:34` log_operation）；驳回 → 填驳回原因，Phase 保持原值；
3. 项目负责人自己改计划时间：直接生效，不走审批（说明第 6 条前半句）。

**入口独立**（§九-4 已裁定）：改期审批只在填报页 Tab2 闭环，不进现有审核中心页面。

**边界规则**：
- **单一 pending**：同一阶段同时最多一个待审申请（沿用 `audit.py:68` 既有语义，report 创建接口同样强制）；
- **负责人直改作废**：项目负责人直接改某阶段计划时间时，该阶段若有 pending 申请自动置 rejected，review_comment 记"负责人已直接改期，申请作废"；
- **无负责人阶段**：未指派阶段负责人的阶段没有申请入口，只有项目负责人可直接改。
- **跨流已知限制（过渡期）**：既有 `/api/phase-change-requests` 流程与填报流共用 `phase_change_request` 表；"负责人直改作废"钩子只挂在填报流 PATCH 上——若负责人经**旧页面**直改计划时间，旧 pending 申请不会被自动作废，之后在 Tab2 批准会以申请中的旧新值覆盖直改结果。过渡期已知限制（本期不改旧页面/旧接口），与 §九-4 入口闭环裁定配套；二期如放开旧入口，需把作废逻辑下沉到共享层。

## 五、页面结构（`/report` 单页 + 弹窗）

```
┌ 信息填报（ReportPage）────────────────────────────┐
│ 筛选栏：搜索(名称/编号) + 状态 + 市场 + 类目 + 重置   │
│   ——与项目列表页同款同逻辑；sessionStorage 进出保留， │
│   刷新页面统一清除                                  │
│ [Tab1 已建项目] [Tab2 我的] [Tab3 待我审批(角标)]    │
│ Tab1：项目卡片表（编号/名称/类目/负责人/市场/状态/   │
│   项目进度）——项目进度 = 名下阶段 progress 均值，    │
│   无阶段显示"—"；按创建日期排序（id 升序）；          │
│   行尾呼吸标识：逾期(暖红) / 即将到期(暖黄)，        │
│   搁置项目与已完成/搁置阶段不标                      │
│   [新建项目]按钮 → 弹窗（§5.1）                      │
│   点项目行 → 展开阶段明细表（§5.2）                  │
│ Tab2 我的：我负责 + 我参与的项目（除项目编号列外与    │
│   Tab1 一致），"我负责/我参与"标记移至名称列，       │
│   按创建日期排序                                    │
│ Tab3：改期申请列表（仅项目负责人可见，其余角色隐藏）  │
└────────────────────────────────────────────────────┘
```

**筛选栏**：四个条件与项目列表页同逻辑——关键词匹配项目名称/编号，状态/市场/类目精确匹配；两个数据版块（已建项目 / 我的）共用同一筛选。

**「我负责」标记口径**（用户 2026-10-30 裁定）：项目负责人与登录填报人匹配即为「我负责」——managed_by 命中账号，或未关联账号时 owner 文本 = 账号名（`is_project_manager`）；其余仅在阶段担任负责人的显示「我参与」。我负责 = 全部修改权限（项目级字段/计划时间/删除/审批），我参与 = 阶段字段部分修改 + 变更申请。

**5.1 新建项目弹窗**：编号自动预览（只读）+ 类目（三选一下拉）+ 名称 + 项目负责人（下拉选人，默认当前用户）+ 市场（10 项下拉）+ 项目状态 + 项目备注 + 阶段批量编辑表格（10 类阶段预填行：类型下拉/计划起止/负责人多选，可增删行、行序即 sequence，行级校验结束>开始）。

**5.2 阶段明细编辑**：字段级可编辑标记由后端下发（§六 GET projects/{id} 返回），前端仅按标记渲染禁用态；**权限判定以后端为准**，前端禁用只是显示裁剪。

## 十二、先例与查证
