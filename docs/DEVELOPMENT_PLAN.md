## 1. 项目概述

### 1.1 背景

团队 20 人，同时在管 15-18 个智能终端（金融自助设备）研发项目，交付周期 2 个月以内。现用 Excel 甘特图手工管理，存在数据不规范、依赖关系不直观、资源负载不可见等核心痛点。

### 1.2 目标

建设一个中小型项目管理平台，将项目管理从"手工 Excel 统计"升级为"结构化数据驱动"，实现：

- 项目全生命周期可视化（甘特图 + 依赖关系）
- 资源负载透明化（谁在干什么、有没有冲突）
- 多项目全局视角（跨项目看风险和进度）
- 管理流程标准化（项目模板化，减少重复梳理）

### 1.3 MVP 范围

| 纳入 MVP | 排除（后续迭代） |
|---------|----------------|
| 项目/阶段/依赖/资源 CRUD | 用户认证 / 权限系统 |
| Excel 导入（现有 18 个项目） | 团队协作填报 |
| 甘特图视图（依赖连线、拖拽改期） | 微信通知集成 |
| 资源负载视图 | 自动周报生成 |
| 3 套项目模板 | 甘特图导出为图片 |
| 返工标记与日志 | 关键路径自动计算 |

### 1.4 运行环境

- **部署形态**: 本地 Web 应用（浏览器打开即用），单用户
- **运行环境**: macOS，Python 3.12 + Node.js v25
- **后续**: 开放团队时迁移至服务器部署

## 2. 技术选型详细分析

### 2.1 后端：Python + FastAPI

| 维度 | 分析 |
|------|------|
| **优势** | ① 开发速度快——FastAPI 自带 API 文档（Swagger UI），写完接口自动生成文档；② Python 生态成熟，pandas/openpyxl 处理 Excel 是强项；③ 异步支持好，后续团队使用时并发不是瓶颈；④ 类型提示强制，代码质量有保障；⑤ AI 辅助开发友好（Pydantic model → 代码生成效率高） |
| **劣势** | ① Python 3.9 是系统自带版本，略旧（3.10+ 的 `match/case` 等特性不可用，但不影响功能）；② 单进程 GIL 限制，但 MVP 单用户场景无影响；③ 相比 Go/Java，超高性能场景不适合（本项目不涉及） |
| **后续影响** | ① 迁移到 PostgreSQL 只需改连接字符串 + 少量 SQL 方言适配；② FastAPI 的 OpenAPI 规范可直接生成前端 TypeScript 类型，前后端对接效率高；③ 后续加 WebSocket（实时协作）有天然优势 |

**备选方案对比**:
- ~~Node.js + Express/NestJS~~：前后端同语言，但 Excel 处理生态弱于 Python，且你团队大概率 Python 基础更好
- ~~Go + Gin~~：性能好，但开发速度慢，Excel 库少，MVP 阶段不适合

### 2.2 数据库：SQLite

| 维度 | 分析 |
|------|------|
| **优势** | ① 零配置——一个文件就是整个数据库，备份/迁移极其简单；② 性能足够——18 项目 × 8 阶段 ≈ 150 条记录，SQLite 轻松处理百万级；③ 不需要额外安装数据库服务；④ Python 标准库自带 `sqlite3` 模块 |
| **劣势** | ① 不支持并发写入（同一时间只能一个写操作）——但 MVP 单用户无影响；② 没有用户权限管理——MVP 不需要；③ 缺少部分高级 SQL 特性（如窗口函数在旧版本受限） |
| **后续影响** | ① 迁移 PostgreSQL 成本极低——ORM（SQLAlchemy）屏蔽了方言差异，改 `DATABASE_URL` 即可；② 数据迁移可导出 SQL 脚本一次性完成；③ **决策建议**：团队协作版上线时（预计 Phase 5+）迁移 |

**备选方案对比**:
- ~~PostgreSQL~~：功能更强，但 MVP 阶段需要安装配置，过度设计
- ~~MySQL~~：同上，且 Oracle 商业风险

### 2.3 前端：React + TypeScript + Vite

| 维度 | 分析 |
|------|------|
| **优势** | ① React 生态最大，组件库和甘特图库选择最多；② TypeScript 类型安全，接口对接不易出错；③ Vite 构建速度快（比 Webpack 快 10-100 倍），热更新秒级；④ AI 辅助开发效率最高（训练数据最多） |
| **劣势** | ① React 学习曲线（对你而言不影响——你不需要写前端代码）；② 依赖包体积相对大（但本地应用无所谓） |
| **后续影响** | ① 后续团队使用时可轻松加权限/协作功能；② React Native 可复用部分逻辑做移动端（如果你将来想在手机上看甘特图）；③ 生态丰富，任何新需求都能找到现成方案 |

**备选方案对比**:
- ~~Vue 3~~：同样优秀，但甘特图库选择略少于 React 生态
- ~~Svelte~~：性能好但生态小，甘特图库几乎没有

### 2.4 甘特图核心组件：dhtmlxGantt（社区版）

| 维度 | 分析 |
|------|------|
| **优势** | ① **功能全覆盖**——支持 FS/SS/FF/SF 四种依赖类型、拖拽改期、资源视图、关键路径、缩放；② 社区版免费（GPL 协议），MVP 阶段无商用成本；③ 中文文档完善；④ 原生支持 JS，可封装为 React 组件；⑤ 性能好，1000+ 任务流畅渲染 |
| **劣势** | ① 社区版功能有限制（部分高级功能如关键路径高亮需 Pro 版）——但 MVP 需求社区版够用；② GPL 协议要求开源（如果你后续要商业化需要购买商业授权）；③ 不是原生 React 组件，需要封装；④ 样式定制有一定学习成本 |
| **后续影响** | ① 如果后续需要关键路径自动高亮、资源平滑等高级功能，需评估是否购买 Pro 版（约 $599/年）；② 社区版功能锁定在 MVP 范围内是可控的；③ 封装层设计好，更换甘特图库的成本可控 |

**备选方案对比**:

| 方案 | 依赖类型 | 资源视图 | 拖拽改期 | 费用 | 结论 |
|------|---------|---------|---------|------|------|
| **dhtmlxGantt 社区版** | ✅ FS/SS/FF/SF | ✅ | ✅ | 免费(GPL) | **推荐** |
| Frappe Gantt | 仅 FS | ❌ | ✅ | 免费(MIT) | 功能不足 |
| Bryntum Gantt | ✅ 全部 | ✅ | ✅ | $2,395+ | 太贵 |
| AG Grid Gantt | 需自建 | ❌ | 需开发 | 商业授权 | 开发量大 |
| 自研 SVG/Canvas | 自由 | 自由 | 需开发 | 免费 | 开发量巨大 |

> **关键决策**：MVP 阶段 dhtmlxGantt 社区版完全够用。关键路径高亮这个功能，我们可以自己在前端算（用拓扑排序算法），不依赖 Pro 版。

### 2.5 Excel 导入：openpyxl + pandas

| 维度 | 分析 |
|------|------|
| **优势** | ① openpyxl 精确控制 Excel 读写（保留格式、处理合并单元格）；② pandas 做数据清洗和批处理效率高；③ 能处理日期序列号转换（`46199` → `2026-07-01`）；④ 可以生成"导入校验报告"——告诉你哪些数据有问题 |
| **劣势** | ① pandas 依赖较重（~30MB）；② 对复杂合并单元格的处理需要额外逻辑 |
| **后续影响** | 导入是一次性功能（后续新项目在平台内创建），维护成本低 |

## 4. 项目模板定义

### 4.1 标准阶段字典（8 个）

| 代码 | phase_type | 中文名 | 说明 |
|------|-----------|--------|------|
| P1 | requirement | 需求评估 | 客户需求/招标要求分析 |
| P2 | configuration | 配置评估 | 硬件配置方案确认 |
| P3 | selection | 模块选型 | 核心模块/器件选型 |
| P4 | industrial_design | 工业设计 | 外观/造型设计 |
| P5 | structure_design | 结构设计 | 整机结构设计（含原"整机设计"） |
| P6 | prototyping | 样机打样 | 首版样机制作 |
| P7 | testing | 联调测试 | 功能/性能验证 |
| P8 | delivery | 交付 | POC/投标/发货/量产保障 |

### 4.2 模板 A：招标/新品研发标准流程

**适用场景**：银行招标项目、新品研发（覆盖国内大多数项目）

```
P1 需求评估 ─┐
P2 配置评估 ─┼── SS(并行启动) ──→  P4 工业设计 ──FS──→ P5 结构设计 ──FS──→ P6 样机打样 ──FS──→ P7 联调测试 ──FS──→ P8 交付
P3 模块选型 ─┘
```

**默认依赖关系**:

| from | to | type | lag | 说明 |
|------|----|------|-----|------|
| P1 需求评估 | P4 工业设计 | SS | 0 | 需求开始后设计可启动 |
| P2 配置评估 | P4 工业设计 | SS | 2 | 配置评估开始2天后设计启动 |
| P3 模块选型 | P4 工业设计 | SS | 3 | 模块选型开始3天后设计启动 |
| P4 工业设计 | P5 结构设计 | FS | 0 | 设计完成→结构开始 |
| P5 结构设计 | P6 样机打样 | FS | 0 | 结构完成→打样开始 |
| P6 样机打样 | P7 联调测试 | FS | 0 | 打样完成→测试开始 |
| P7 联调测试 | P8 交付 | FS | 0 | 测试完成→交付 |

**默认工期（天，可调整）**:

| 阶段 | 默认工期 |
|------|---------|
| P1 需求评估 | 5 |
| P2 配置评估 | 5 |
| P3 模块选型 | 7 |
| P4 工业设计 | 7 |
| P5 结构设计 | 14 |
| P6 样机打样 | 15 |
| P7 联调测试 | 7 |
| P8 交付 | 10 |

### 4.3 模板 B：量产交付流程

**适用场景**：海外量产项目（俄罗斯/越南/侧柜类）

```
P5 结构设计 ──FS──→ 图纸归档 ──FS──→ BOM/激活 ──FS──→ 投料 ──FS──→ 首批生产保障 ──FS──→ 发货
```

> 模板 B 的阶段不使用 P1-P8 的标准编码，而是用项目特定的交付阶段。

### 4.4 模板 C：定制/改造流程

**适用场景**：定制机、小批量改造项目

```
P1 需求分析 ──FS──→ P4 工业设计(可选) ──FS──→ P5 结构设计 ──FS──→ P6 样机打样 ──FS──→ P7 测试 ──FS──→ P8 发货
```

### 4.5 返工机制

返工不是特殊的"返工类型"，而是通过 **状态回退 + 返工日志** 实现：

1. 任意阶段可从 `进行中/已完成` 回退到 `未开始` 状态
2. 每次回退记录一条返工日志（日期 + 原因 + 回退目标阶段）
3. `rework_count` +1，甘特图上该阶段显示橙色返工标记
4. `actual_finish` 清空，重新走流程
5. 所有返工记录永久保存，可用于项目复盘

## 5. 开发路线图

### 5.1 总览

| Phase | 名称 | 周期 | 核心交付 |
|-------|------|------|---------|
| **P1** | 数据层 + API | 第 1 周 | 数据库 + FastAPI CRUD + 3 套模板预置 |
| **P2** | Excel 导入 | 第 2 周 | Excel 解析器 + 数据清洗 + 18 项目入库 |
| **P3** | 甘特图主界面 | 第 3 周 | dhtmlxGantt 集成 + 依赖交互 + 任务编辑 |
| **P4** | 资源视图 + 收尾 | 第 4 周 | 人员负载视图 + 多项目总览 + 测试 |

### 5.2 Phase 1：数据层 + API

**目标**：搭好后端骨架，能通过 API 操作数据。

| 任务 | 产出 |
|------|------|
| 项目脚手架搭建 | FastAPI 项目结构 + 虚拟环境 + 依赖管理 |
| 数据库模型实现 | SQLAlchemy models（6 张表 + 关联表） |
| 数据库迁移脚本 | `init_db.py`，一键建表 + 索引 |
| CRUD API 实现 | 项目/阶段/依赖/资源/模板 的增删改查接口 |
| 模板预置数据 | 3 套模板 + 标准阶段字典写入数据库 |
| 示例数据生成 | 1-2 个完整示例项目（含依赖、人员分配） |
| API 文档 | FastAPI 自动生成 Swagger UI (`/docs`) |

**验收标准**：
- ✅ `python init_db.py` 一键建库成功
- ✅ `uvicorn main:app --reload` 启动成功
- ✅ `localhost:8000/docs` 能看到所有 API 接口
- ✅ 能通过 API 创建项目、添加阶段、建立依赖
- ✅ 3 套模板预置成功，可查询

### 5.3 Phase 2：Excel 导入

**目标**：把现有 18 个项目导入系统。

| 任务 | 产出 |
|------|------|
| Excel 解析器 | 解析两个 Sheet，提取项目/阶段/人员数据 |
| 数据清洗规则 | 日期序列号转换、多空格人名拆分、空行跳过 |
| 人员自动建库 | 从 Excel 提取所有人名，自动创建 RESOURCE 记录 |
| 批量导入接口 | `POST /api/import/excel`，上传文件批量导入 |
| 导入校验报告 | 返回导入结果：成功 N 条、失败 N 条、失败原因 |
| 18 项目实际入库 | 所有历史项目数据在系统中可见 |

**验收标准**：
- ✅ 原始 Excel 能完整解析，无报错
- ✅ 日期序列号正确转换（46199 → 2026-07-01）
- ✅ 多人字段正确拆分为独立的 resource 关联
- ✅ 导入后能在 API 中查询到 18 个项目及其阶段
- ✅ 生成导入报告，列出所有数据异常

**已知数据清洗挑战**:

| 问题 | 处理方案 |
|------|---------|
| Excel 日期序列号（46199） | `(date(1899,12,30) + timedelta(days=serial))` 转换 |
| 文本日期（`2026/-/--`） | 标记为"待确认"，`plan_start` 设为 null |
| 多人字段（空格分隔） | 正则拆分 + trim，创建/匹配 RESOURCE 记录 |
| 空行/备注行 | 检测连续空列，自动跳过 |
| 阶段名不一致 | 映射表：表中的各种阶段名 → 标准 phase_type |
| 单元格内换行 | 清除 `\n`，取第一行有效内容 |
