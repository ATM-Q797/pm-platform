## §2 批次任务与设计（主 agent）

**任务**：8-3 按项目维度的历史趋势（PHASE8_PLAN §三，方案 A）——项目详情页新增「进度趋势」区。

**设计要点**（依据 §三已批准条款，本轮细化为实施面）：

1. **建表**（`deploy/migrate_v6.sql`，v5 已被站内通知占用——同 P1 批判例）：
   - `project_snapshots(project_id, snapshot_date, metrics JSONB, project_code, project_name, created_at)`
   - 唯一约束 `(project_id, snapshot_date)`（幂等 upsert，与全局快照同款）
   - 外键 `project_id ON DELETE SET NULL`（不用 CASCADE——用户裁定「删项目要能追溯」）
   - 索引：project_id、snapshot_date、created_at
2. **采集**（`services/snapshot.py` 扩展）：与全局快照同一 crontab 任务内写入；只拍**在办项目**（状态 ∈ {未开始, 进行中}，排除专项）；同日重复触发 upsert 幂等。
3. **降采样**（分层，§三 口径③）：90 天内日粒度 → 2 年内周粒度（周一锚点）→ 以上月粒度（月初）；migrate_v6 附维护函数，crontab 周任务执行。
4. **读取**（`routers/analysis.py` 扩展——**评审 #16 端点落点补回**）：`GET /api/projects/{id}/trend?days=30|90|365` 返回日/周/月混合点列；admin「历史项目」入口按 `project_code` 查被删项目曲线（SET NULL 后仍可查）。
5. **前端**（`pages/ProjectDetailPage.tsx` 扩展）：「进度趋势」区两条线——计划累计完成度 vs 实际累计完成度，缺口即偏差；延期/冲突事件点叠加（P2 事件标记随本批埋点先行，标记渲染在 P2 批细化）；时间窗 30/90/365 切换。
6. **降级口径**：缺失日期断开不补零（§3.5 验收）；数据不足 7 天显示「数据积累中（尚需 N 天）」（§七 风险对策）。

**验收**（§3.5）：当日快照末点与看板当日数字一致；停机缺口断开非补零；同日重复触发不产生两行；被删项目按编号可查历史曲线。
