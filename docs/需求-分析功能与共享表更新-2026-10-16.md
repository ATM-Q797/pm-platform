# 需求文档：分析功能与共享表更新（2026-10-16）

## 背景

- 平台 2026-10-16 生产数据：59 项目 / 297 阶段，22 进行中，10 个延期项目，资源冲突 9 组全部集中在张晓平。
- 基于生产数据的分析建议已给出（资源负载预警、阶段瓶颈分析、健康度评分、市场维度分析可直接开发；里程碑达成率、历史趋势、返工分析缺数据）。
- 用户判定：历史趋势分析的快照机制有价值，要求重点规划。
- 用户痛点：项目填报在腾讯共享文档上维护，导入平台目前要"下载→导出→再上传"，想加一个"共享表数据更新"按钮。

## 需求 1：历史趋势分析 — 状态快照机制

### 目标

定时把全局状态存下来，积累后画趋势曲线。回答：积压在变多还是变少？延期在恶化还是好转？负载在集中还是均衡？

### 快照表 status_snapshots

| 字段 | 作用 |
|------|------|
| id | 主键 |
| snapshot_date | 快照日期（唯一约束，防重复） |
| metrics | 指标 JSON |
| created_at | 记录时间 |

### metrics 指标口径

复用 dashboard.py 现有统计逻辑，同一口径保证与看板数字一致：
- 项目各状态计数（进行中/已完成/搁置/未开始）
- 延期项目数、延期天数分布（P50/P90）
- 延期阶段数、即将到期阶段数
- 冲突数
- TOP 过载人员（峰值并行数）
- 未完成阶段数、平均项目完成度

### 定时执行方案

生产环境是 Docker Compose + gunicorn 多 worker。多 worker 下不能起后台线程定时器（会重复执行）。两个方案：

- 方案 A：独立快照服务（Compose 加同镜像单进程服务）— 自包含但多一个常驻部件。
- 方案 B（推荐）：宿主机 crontab 每天凌晨调幂等 API（POST /api/snapshots/run，先查当天快照存在则跳过）。改动最小，与 update.sh 靠宿主机跑的运维模式一致。

### 里程碑（2026-10-16 用户裁定：全自动积累，无手动按钮）

- M1：快照表 + 每日快照 API（幂等）— crontab 自动积累，无任何 UI 按钮
- M2：趋势分析按钮 + 弹窗趋势图 — 前端入口按钮，点击弹窗显示趋势图；图表库选型（前端目前无图表库，package.json 只有 dhtmlx-gantt 和 antd；候选 ECharts/Recharts/轻量 SVG）

### 趋势图数据内容论证（2026-10-16）

设计原则：① 每个指标回答一个明确管理问题 ② 口径与 Dashboard 一致 ③ 只收数据就绪的指标 ④ 快照存原子计数，比率/吞吐在查询时由快照差分计算——未来加图不用改历史快照结构。

纳入指标：

| 组 | 指标 | 回答的问题 | 数据就绪 |
|---|---|---|---|
| 交付健康 | 延期项目数、延期率（分母=进行中） | 交付纪律在改善还是恶化 | ✅ |
| 交付健康 | 延期深度 P50/P90 | 延期是普遍轻微还是个别严重 | ✅ |
| 交付健康 | 7 天内到期阶段数 | 未来一周交付压力 | ✅ |
| 规模吞吐 | 项目总数、各状态计数 | 项目池扩张还是收缩 | ✅ |
| 规模吞吐 | 每周完成阶段数（快照差分） | 团队消化速度变化 | ✅ |
| 规模吞吐 | 未完成阶段数 | 剩余工作量趋势 | ✅ |
| 资源 | 冲突对数 | 资源紧张度 | ✅ |
| 资源 | TOP3 峰值并行均值 | 负载集中度（比单人峰值稳） | ✅ |
| 资源 | 活跃人员数 | 实际投入人力面 | ✅ |
| 流转 | 每期新增项目数 | 需求流入速度 | 待查 created_at 字段 |
| 流转 | 转搁置项目数 | 需求冻结速度 | ✅ |

明确排除（数据不支持）：里程碑达成率（actual_end 3.5%）、返工率（记录 0 条）、平均项目完成度（口径易误读，用吞吐量代替）。

展示口径：天级快照、周级展示（周一为锚点），30/90/180 天范围切换；弹窗分三个 tab：交付健康 / 规模与吞吐 / 资源。

### 注意

- 无历史回填：趋势从上线日起算，提前对齐预期。
- 新增 1 张表，migrate_v3.sql 有先例，风险小。

## 需求 2：共享表数据更新按钮

### 2026-10-16 用户裁定：直连不可行，改走自部署共享云文档路线

验证结论：服务器出网不可达 + 腾讯文档无法匿名下载（两个前提均不成立），直连方案排除。
用户新方向：**寻找开源可自部署的共享云文档（类似腾讯文档），部署后形成自己的共享文档库，平台直连它。**

### 开源候选（初步调研，需用户选型确认）

| 方案 | 形态 | 协作能力 | 部署复杂度 | 与平台对接 |
|------|------|---------|-----------|-----------|
| **OnlyOffice Docs**（社区版） | 文档/表格/幻灯片 | 实时协同编辑 | 中（Docker 镜像） | 文件存 ownCloud/Nextcloud，有 API |
| **Collabora Online**（开发版免费） | LibreOffice 内核在线表格 | 实时协同 | 中（Docker + 反代） | 同上，配 Nextcloud 使用 |
| **Seafile + OnlyOffice** | 网盘+在线协同组合 | 实时协同 | 中高（两服务） | Seafile API 成熟 |
| **EtherCalc** | 轻量在线表格 | 弱协同（轮询） | 低 | 极简，但功能太弱，不推荐生产 |
| **Grist** | 结构化表格（类 Airtable） | 实时协同 | 低中（Docker 单容器） | **有完整 REST API，导出 xlsx 一行命令** |

### 初步推荐：Grist 或 OnlyOffice+Nextcloud

- **Grist**：如果填报本质是"结构化表格数据"（项目/阶段/日期/状态），Grist 最贴合——数据本身就是结构化的，REST API 直接取数，甚至可以让平台直接读 Grist 的数据表，跳过 Excel 中转。
- **OnlyOffice + Nextcloud**：如果填报人习惯"Excel 样子的表格"，这条路线保留 Excel 形态，协同编辑体验最接近腾讯文档，平台通过 Nextcloud WebDAV/API 定时取 xlsx 文件喂给现有 excel_importer——**导入解析逻辑零改动**。

### 决策点（需用户确认）

1. 填报人是否必须保留 Excel 操作习惯？（是 → OnlyOffice+Nextcloud；否 → Grist）
2. 部署资源：服务器是否有多余 2G+ 内存跑新服务？
3. 填报人数量与并发（协同编辑人数）。

### 对接架构（选定后）

```
[共享云文档（自部署）] --定时/手动拉取--> [后端新端点 /api/import/shared]
     xlsx/结构化数据                          复用 excel_importer
                                                  ↓
                                          preview 差异报告 → 确认导入
```

前端"共享表数据更新"按钮 → 调 /api/import/shared/preview 弹差异 → 确认 → 导入。与现有手动导入共用全部解析与报告逻辑。
